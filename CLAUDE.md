# StarCraft II: Ghost Ops - rules for sessions

## Automatic test launches of StarCraft II (Owner rule, 2026-10-19)

Use `python tools/test_launch.py --mission M --preset P --seconds N [--keep] [--shot FILE --shot-at S]`
(helpers: `tools/monitors.py`, `tools/mute_process.ps1`). Do not start the game for tests any other way.

1. The test game runs in a small ordinary window (start size 1024x768, `-displaymode 0 -windowwidth/-windowheight/-windowx/-windowy`)
   on the SECOND monitor. Monitors, work areas and scaling are read from Windows every time (the second monitor may be left of the
   primary one and have negative coordinates; never hard code X=1920). No second monitor: a small window on the available screen,
   and say so in the report.
2. The window is placed by the launch parameters; `SetWindowPos` with `SWP_NOACTIVATE` only corrects it if needed. No Always on Top,
   no repeated focus forcing, no activation of the window without a concrete need.
3. Sound is off: only the audio sessions of OUR process are muted (`mute_process.ps1`, checked: `sessions=1 confirmed=1`). The Windows
   master volume, other applications and the Owner's game settings are never touched. The normal GUI / CLI launch keeps sound and the
   normal window (`launch_command` has no test parameters).
4. Only the process started by the test launch is controlled (new `SC2_x64.exe` PID, window ownership checked). If a game is already
   running, the test launch is refused: the Owner's game is never moved, minimised, muted or closed.
5. The Owner's permanent settings (Variables.txt, graphics, volume) are not changed; everything is a parameter of one launch.
6. Screenshots of the test window: `python tools/sc2_ui.py PID shot FILE` (PrintWindow of OUR window only; never grab the screen area, a DPI-unaware process
   captures the wrong monitor). The capture returns an ALL-BLACK frame at random moments (measured 2026-10-23, also when nothing covered the window): a black frame is a
   LIMIT OF THE CAPTURE, never a result about the map; take a burst (`burst` op of `tools/ce0_steps.py`: n shots, black ones dropped) or repeat the shot a moment later,
   and report "no picture obtained" instead of a verdict when none is clean. Keys and clicks into the test game
   (`sc2_ui.py PID key ...`, posted window messages, no focus change) and any size other than 1024x768 must be announced to the Owner before
   such a launch. Saves made by such tests (`GHOSTOPS_TEST_*.SC2Save`) are deleted afterwards; the mute loop must run for the whole life of a
   kept game (`mute_process.ps1 -Seconds N`).
7. Do not claim "no focus stealing" unless a real launch has confirmed it.
8. Developer presets (`*_dev`) put test units (enemy Barracks and the like) on the map: their `.SC2Map` must never stay in
   `Maps\GhostOps` (the Owner saw such Barracks once). `test_launch.py` uninstalls them after the run; with `--keep` do it yourself
   (`python tools/build.py uninstall --mission M --preset P_dev`).

## Project

- One repo, branch `main`; no commit / push / publication without a separate explicit permission of the Owner.
- Galaxy sources stay ASCII; visible texts go through the string table (`StringExternal`, `config/*.json` texts).
- After any real launch read the matching new `Documents\StarCraft II\GameLogs\<time> ScriptError.txt`; the campaign-init
  "not authorized" lines are known noise of launches from the Maps folder, a compile error is not.
- The dev-only preset `tactical_dev` (TRaynor02) writes `Documents\StarCraft II\Banks\GhostOpsDevTac.SC2Bank` and can script the nuclear
  strike test (`tactical.autotest.mode`); it is hidden from the GUI and never part of a playable build.

## Campaign, saves and probes (Owner rules, 2026-10-20)

- The campaign state (`%APPDATA%\GhostOps\campaign.json`) and the Owner's saves / Banks are never filled with test data: tests and probes use their own files (`GHOSTOPS_CAMPAIGN_FILE`, `GHOSTOPS_BANK_DIR`,
  saves named `CE0_*` that are deleted afterwards). A test budget of a standalone map test is never written into the campaign.
- `tools/ce0_session.py stop` uninstalls the preset's map: use `--keep-map` for any map that is not a hidden dev map. The CE-0 probe (`ce0` key) exists only in hidden `*_dev` presets.
- A started operation's map file is immutable (unique name per operation); do not rebuild over it and do not delete it while a save may depend on it.
- Game voice WAVs stay local (git-ignored); only the manifest `assets/audio/SOURCES.md` and the recipes `assets/audio/clips.json` are published (`python tools/prepare_audio.py` recreates the clips from the installed game; `--no-voice` builds without added voice, the map file gets `_novoice`; a test copy of it is never left in `Maps\GhostOps`). No commit of the voice lab tree, installs, CASC data, original maps, saves or Banks.
- Documentation separates: implemented and confirmed / agreed / architectural requirement / open question / technical check. Experimental numbers (prices, limits, waves) are never called Owner-approved.
- Seventh task: maps changed after a started playthrough get a new file name (`GhostOps_<Mission>_r2_<profile>.SC2Map`, `output_map_file` in the adapter); the old-named maps are never overwritten (a save is bound to the map path). Rebuild old ones from the commit that built them if they were touched by mistake.
- Test-launch guard (Owner, 2026-10-21, after a full screen test game): `build.start_detached` is the ONLY function that starts a game process; without `owner=True` (or with the env var `GHOSTOPS_TEST`, which every test tool sets by importing `test_launch`, also when it drives the GUI) it calls `test_launch.launch_test_game`: window 1024x768 (`-displaymode 0`), second monitor if present (primary otherwise), our process muted, never raised / topmost, and the real window (not maximised, not full screen, size, inside the work area) is verified - a non-compliant test window is closed (our pid only). Ad-hoc scripts must not call `build._raw_start` or `SC2Switcher` themselves (`tests/test_launcher.py::TestGameLaunchGuard`). The Owner's normal GUI / CLI launch (`owner=True`, no test env) stays unchanged.

## Galaxy / build traps found with the defence profile (2026-10-21)

- A very long single-statement string concatenation or a huge command function gives an unlocatable "Script load failed: syntax error": split the statement / the function (`tools/last_script_error.py` prints the compile and load lines).
- An ability that targets a structure (turret) needs `<Arc value="360"/>`, otherwise the order is invalid.
- `AIAttackWaveSend(..., wait=true)` BLOCKS the thread until the wave is over; the attack sources run as parallel threads: shared buffers must be emptied before the send.
- The original starts the AI in the intro, before the mission start hooks: a mode flag the wave hooks test must be set by a hook before `TriggerExecute(gt_StartAI` (see `build.apply_ce0`).
- A destroyed unfinished construction and a cancelled one look the same to the script after the unit is gone; the defence kit rule tells them apart by a drop of life (4 s) or an enemy within 6.

## Owner versions, development and waiting for a free game (2026-10-21)

- The Owner plays the INSTALLED map files. A protected map (`build/owner_maps.json`: `python tools/isolation.py status`; every map the Owner's normal launch started is registered automatically) is never rebuilt, replaced, uninstalled or renamed - `build.py` refuses (CLI, launcher and campaign window all go through it), and `prepare()` starts it as it is. Development goes under its OWN hidden preset name (`defence_next`, `defence_next_dev`, ... ending in `_dev` when it has the probe) and gets its own map file; `python tools/isolation.py protect-all` registers the installed maps once. Do not edit the config of a preset the Owner plays (`defence`): copy the change into the `*_next` preset. No second worktree is needed for this.
- In-game tests never wait inside the conversation: put a prepared, bounded scenario into the queue (`python tools/test_queue.py enqueue --label L --mission M --preset P_dev -- python tools/ce0_steps.py tests/scenarios/X.json`), then do the work that needs no game. The detached runner waits while ANY SC2 process exists (5 s checks, nothing closed or changed), waits 10 s after it disappears, re-checks before the launch and runs the jobs one by one through the test-launch guard. `status`, `cancel [JOB|--all]`, `stop` / `go`, `resume JOB` (an interrupted job is never restarted automatically). The queue closes only a test game whose pid AND creation time it recorded; never kill an SC2 process by name. Pending checks are reported as pending, never as done.
- A test must not touch the Owner's data: jobs use their own campaign file / bank directory / session state (`GHOSTOPS_*` variables set by the runner); probes write only the `GhostOpsDev*` Banks; saves are `CE0_*` and are deleted afterwards.
- Replica TEXTS come from the shared lines table of the voice lab (`build/shared_lines_dir.txt`; `docs/ARCHITECTURE.md` "Shared lines table"): edit a text in the studio or the table, not in `config/*.json` (the config text is only the fallback). `tools/lines_table.py` is an unchanged copy of the lab module - do not edit it here. Tests must not read the lab folder.

- Compare with the ORIGINAL before blaming the mod: profile `orig_trace_dev` (original mission + trace only) and the `TRACE` / `arr` probes of the `*_dev` profiles; a scene of ours must not take the shared trigger queue before `gt_StartTimers` (it delays the original timers); a black screenshot is a capture limit (rule 6 of the first section), not a result, and the original pans the camera to the first wave at about 84 s (a screenshot test must wait for it).

## Developing, checking and handing over missions to the Owner (Owner order, 2026-10-24)

This is the one place for the rules; `docs/MISSION_ROADMAP.md` 3.1 holds the queue and links here. Proofs and logs stay in the existing documents (roadmap, contract, RESEARCH); the number of green tests is never a result description.

- **A. The unit of work is a finished game episode or a player action.** Define a few observable criteria for the task. An ability includes the button, the hotkey, the tooltip, the aiming, the visible cost or remainder, the model, the effect and the result of the action; interface and visual result are part of the mechanic. Example (container): select the Firebat -> press C -> see the place and the range -> place a recognisable barrel -> see the expense -> attack it -> get a clear explosion.
- **B. Checks match the claims.** Unit tests and scripted orders confirm their own part. A control claim needs at least one pass of the action through the REAL game interface (real keys / mouse of the protected test launch). Balance and how interesting a run is are judged by the Owner; a passive autonomous run finds gross problems but never confirms playability.
- **C. After two attempts without new information change the approach:** name the obstacle, revise the hypothesis or the way of checking, continue the independent items; do not repeat identical runs to close an item formally. Launch, ordinary save / load, resource accounting and the victory condition are never dropped from the required checks; a blocked required check is reported as a concrete blocker. An unchecked minor detail must not stop the whole queue: list it separately and never call it verified.
- **D. Check in proportion to the change.** Repeat confirmed scenarios only when a change touches them, after a new failure or a concrete doubt; for shared modules count the affected missions. No full playthrough for a local effect that a short scenario shows.
- **E. Balance moves in small groups of related parameters.** First state the wanted player behaviour; pick experimental numbers yourself inside the agreed design, keep them in the config and list them in the report (never "approved"). Never win an autonomous scenario by arbitrarily strengthening troops; do not change many independent parameters at once without an explanation.
- **F. A hand-over is understandable.** Per mission: one clearly marked current recommended version and, separately, the new experimental one when it exists (difficulties stay inside a version). Old maps and operation sets stay for continuing and for loading saves; a started operation is never rebuilt in place. The launch mode says plainly whether the run takes part in the campaign economy. The protected test launch and the free-game queue rules above stay in force.
- **G. Work autonomously inside the agreed task.** No separate permission for each technical step; on an obstacle continue the independent work and report the concrete problem. The final report starts with: what is ready to check and where; what changed; the 2-3 things for the Owner to judge; the remaining limits.
- **H. Shared mechanics survive the move to the next mission (Owner, 2026-10-25).** An ability that already exists in a finished mission (turret ground salvo, rebel labels, grenade launcher, detector analysis, containers) is reused through its shared module and settings, not rewritten per mission; its availability in each mission is an explicit setting recorded in the applicability table of `docs/MISSION_ROADMAP.md`. When a mission is built or revised, check that the controls, tooltips and aiming of the carried mechanic still work (real keys and mouse) and that it is not silently missing; "in the code / in the config" is never the same as "works in the installed map".
- **Traps found by the r3 package (2026-10-25).** A new ability on the Ghost card must get a free slot (`grenade.card_row/card_col`): slot (1,1) is covered by the stock card button (it showed a grey button). An ability in a campaign map the tech tree does not know needs `TechTreeAbilityAllow`. A unit-targeted ability with `TargetFilters` rejects ground clicks: use `TargetFilters value=""` plus an area effect (point targets valid). The test queue runner dies when `tmp/testqueue/queue.json` is held open by another process: rename the file and put a copy back (`Move-Item`), never kill other processes.
- **Traps found by the r4 package (2026-10-26).** A stock `CAbilEffectTarget` (Snipe) walks the unit to a click beyond its stock range (10) however `Range` / `RequireTargetVision` are overridden: replace the order at the Execute stage by one inside the range and do the shot at the Complete stage. The nuclear strike keeps the stock "target must be visible" requirement unless `tactical.nuke.require_vision` is set false explicitly (the Ghost walked into its own blast). A paused detector does not detect (a detector test must not pause the detector). A paused Firebat still flames a container next to a dummy once released: pause / remove dummies. `GameSetGlobalTimeScale` (probe `slow`) catches frames of fast effects.

- **Traps found by the r5 package (2026-10-27).** A group loop inside a group loop of ONE Galaxy function ends the outer loop after its first unit (the second Ghost was never scanned): collect the positions first, then call a function with its own single loop. An actor / model effect for a unit that the player does not see is never drawn: for a circle in the fog the unit must be visible (the early warning reveals the detector for half a second and lets the stock radar draw the circle). `cmd` steps of `ce0_steps.py` return no text: add an `expect` step with a regex for the log lines you need, and put it BEFORE a step that may fail. Screenshots only with PrintWindow of OUR window (`sc2_ui.py`, `tools/workshop_window_check.py`); an `ImageGrab` of a screen area from a DPI-unaware process captured the Owner's browser once (deleted). The queue builds the map of a job when its turn comes: a Galaxy compile error in an `ce0_extra.galaxy` breaks every later job, so run `build.py verify` and do not reference globals of a module the older profile lacks (an r4 build has no r5 symbols); do not edit sources while a job that builds is running. Pixel coordinates of scenario clicks are CLIENT coordinates of the 1024x768 game area (a screenshot has a 13 px / 58 px frame: image x - 13, y - 58). Closing an own test game only through `isolation.close_owned` (pid + creation time + job); the creation time is read with GetProcessTimes (`procs`), never with the slow PowerShell query (17-25 s while the game runs; it made the install guard take 26-42 s). A paused unit does not detect and an invulnerable unit shows a dome: do not mistake it for a beacon.

- **Traps found by the Epidemic r7 package (2026-10-28).** The `Execute` stage event of a target ability fires when the ORDER STARTS (the ship has not flown to the point, nothing is paid): use `Complete` for "the cast really happened". `UnitAbilityReset(unit, abil, c_spendLocationUnit)` restores ONE charge per call (loop until `UnitAbilityChargeInfo` is full). A missile launched by an ability effect without an action actor (`CActorAction` with `LaunchSiteOps`) starts on the GROUND under the caster and rolls: give it an action actor (`SOpAttachCenter` = hull height; the stock Ravager bile is the sample); the mover Ballistic with `FlightTime` and gravity 2h/T^2 falls straight, `ArrivalTestType 3D`; do the damage from the impact EFFECT (`TriggerAddEventPlayerEffectUsed`), never from an animation. The original mission pans the camera at the start of a night wave: a posted real click then lands elsewhere (`retry` op of `ce0_steps.py` repeats a real input until a probe confirms it). Screen calibration of the 1024x768 test window: the ground point of the camera is at client (514, 378), 46 px per cell in x, 38 px per cell in y. The Swann hellions appear at about 147 s of the mission (wait with `until`). After the dawn the Hercules transport ability is off for an empty ship: use the `*_raid_dev` profile (night 600 s) for a long raid. The test game sometimes exits on its own or loads a save for more than a minute: poll for 100 s before judging. A `Marine` right click on the Hercules does not board it; `L` + click boards one unit per click and is unreliable.

- **Traps found by the fold / Tychus package (2026-10-27).** A unit test that calls `build.main(['launch', ...])` for a mission WITH presets really prepares, installs and starts the game (through the test guard it opened a window on the second monitor): tests pass `--print-only`. Any file of `core/`, `adapters/<mission>/`, `config` and `tools/build.py` is an input of the build digest: do not edit them while a queued job is preparing. Chat probes are sometimes lost when the game is busy: repeat harmless ones with the `until` step (it needs a `mark` before it, and `expect` only sees lines after the LAST mark). A charge restores only with `TimeUse` inside the `Charge` element. A `CActorRange` is drawn only for a selected unit: use a splat actor for a permanent ground circle. The Galaxy type of a text tag is `int` (no `texttag`). The decoy is given to the neutral player so that the Protoss (which pick enemies only) ignore it while the Zerg attack it by an explicit order, without any alliance change: NOT yet confirmed in the game (scenario ty_v1 is prepared).
